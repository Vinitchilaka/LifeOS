================================================================================
          LIFEOS BACKEND - SPRING BOOT & SECURITY INTERVIEW QUESTIONS
================================================================================

This file contains the core technical interview questions related to the features 
implemented in LifeOS, along with senior-level answers you can say firmly to impress 
interviewers.

--------------------------------------------------------------------------------
Q1: Why should you disable Open Session In View (OSIV) in a production Spring Boot 
    application? (spring.jpa.open-in-view=false)
--------------------------------------------------------------------------------
ANSWER:
"By default, Spring Boot sets OSIV to true, which keeps the Hibernate Session 
(database connection) open for the entire duration of an HTTP request, including 
during view rendering or JSON serialization in the Controller. 

In production, under high traffic, this is a major performance risk because database 
connections are held open longer than necessary, quickly exhausting the connection 
pool (HikariCP) and leading to request timeouts. 

By disabling OSIV, we enforce strict transaction boundaries. The database connection 
is opened and closed strictly within the service layer transaction (e.g., @Transactional). 
To prevent LazyInitializationException in the controller, we fetch required lazy 
relationships in the service layer using JPQL 'JOIN FETCH' or map entities directly 
to DTOs."

--------------------------------------------------------------------------------
Q2: Why must you avoid using Lombok's @Data annotation on JPA Entities?
--------------------------------------------------------------------------------
ANSWER:
"Using @Data on a JPA entity is an anti-pattern. @Data automatically generates 
equals() and hashCode() using all fields of the class, including the database ID 
and lazy-loaded associations.

This causes two major issues:
1. Hash Collisions in Collections: Before an entity is saved, its ID is null. 
   Once saved, its ID is populated. If you add a new entity to a HashSet before 
   saving it, its hashcode will change after saving. As a result, you will not 
   be able to find or remove that entity from the HashSet, causing memory leaks 
   or logic bugs.
2. LazyInitializationException or Infinite Recursion: If @ToString is generated, 
   printing the entity can trigger lazy-loading of associated entities outside 
   of a transaction, throwing an exception or causing infinite loops in 
   bidirectional relationships.

For JPA entities, it is best practice to use @Getter and @Setter at the class 
level, and write custom equals() and hashCode() methods using a stable business 
key (like email or UUID), or rely on standard database ID comparison."

--------------------------------------------------------------------------------
Q3: Why do we use custom DTOs (Request/Response) instead of exposing JPA Entities 
    directly in REST Controllers?
--------------------------------------------------------------------------------
ANSWER:
"Exposing JPA entities directly in REST endpoints is a major security and 
architectural risk. We use DTOs to address three key concerns:

1. Mass Assignment Vulnerability: If a controller accepts a JPA entity directly 
   in a POST/PUT request, a malicious client can include fields they shouldn't 
   have access to (e.g. status = true, emailVerified = true, role = ADMIN). 
   Spring/Hibernate will bind these fields directly to the entity and save them 
   to the database. DTOs restrict input to only the fields allowed to be modified.
2. API Decoupling: DTOs separate our database schema from our external API contract. 
   We can rename database columns or change entity relationships without breaking 
   client-side applications.
3. Preventing Data Leakage: We should never return sensitive fields like hashed 
   passwords back to the client. A Response DTO ensures we only return safe fields."

Q4: Why can we safely disable CSRF protection in a stateless REST API using JWT?
--------------------------------------------------------------------------------
ANSWER:
"CSRF (Cross-Site Request Forgery) attacks rely on session-based cookies. When a 
browser makes a request to a website, it automatically attaches any session cookies 
associated with that domain. If a user is logged into their bank and visits a 
malicious site, the malicious site can forge a request to the bank, and the browser 
will auto-send the session cookie.

In our stateless REST API, we do not use cookies or server-side sessions. Instead, 
we use JWT tokens stored on the client side (like localStorage or memory). The client 
must explicitly attach this token in the 'Authorization: Bearer <token>' header for 
every request. Since browsers do not automatically append custom headers to cross-site 
requests, a malicious site cannot forge requests to our API. Therefore, our API is 
naturally immune to CSRF, and we can safely disable it."

Q5: What is the difference between a Servlet Filter and Spring's DispatcherServlet 
    concerning security?
--------------------------------------------------------------------------------
ANSWER:
"Servlet Filters operate outside and before Spring MVC's DispatcherServlet. 
Spring Security itself is built on a chain of filters (SecurityFilterChain).

It is crucial to perform JWT validation in a Servlet Filter rather than in the 
DispatcherServlet or Controllers because:
1. Early Rejection: If a request carries an invalid, malformed, or expired token, 
   we want to reject it immediately (returning HTTP 401/403) before the request 
   reaches Spring MVC routing, saving server CPU and memory.
2. Standard Security Context: Filters run early, allowing us to populate the 
   SecurityContextHolder before any controller logic executes, ensuring that 
   endpoint authorization is enforced correctly."

Q6: How does @Transactional work internally under the hood?
--------------------------------------------------------------------------------
ANSWER:
"Spring's @Transactional annotation works using Spring AOP (Aspect-Oriented 
Programming) and Dynamic Proxies.

When a method is marked as @Transactional:
1. Spring wraps the bean in a Proxy Object.
2. When a caller invokes the method, the call goes to the Proxy first.
3. The Proxy intercepts the call, obtains a connection from the DataSource, 
   and starts a database transaction by setting autoCommit to false.
4. The Proxy then delegates the call to the actual target service method.
5. Commit: If the method completes successfully, the Proxy calls commit() on 
   the connection.
6. Rollback: If the method throws a RuntimeException or Error, the Proxy catches 
   it and calls rollback().
7. Finally, it closes and returns the connection to the connection pool."

--------------------------------------------------------------------------------
Q7: What is the self-invocation problem with @Transactional?
--------------------------------------------------------------------------------
ANSWER:
"The self-invocation problem occurs when a non-transactional method inside a class 
calls a @Transactional method inside the same class.

Because the call originates from within the same class, Java uses the 'this' 
reference instead of calling the method through Spring's Proxy Object. Since the 
Proxy is bypassed, the transaction interception logic never executes, and the database 
operation runs without a transaction. To fix this, the @Transactional method must 
be moved to a separate bean, or the class must inject its proxy self."

Q8: What is the difference between Password Hashing and Password Encryption?
--------------------------------------------------------------------------------
ANSWER:
"Password Encryption is a two-way function. You encrypt plaintext into ciphertext, 
and you can decrypt it back to plaintext if you possess the secret key. 
We should never encrypt passwords.

Password Hashing is a one-way cryptographic function (like BCrypt). Once a password 
is hashed, it is mathematically impossible to reverse-engineer it back to plaintext. 
During login, we take the raw incoming password, hash it with the stored salt, 
and compare the resulting hash with the stored hash using passwordEncoder.matches(). 
This ensures that even if our database is leaked, the plaintext passwords remain secure."

Q9: Why did you implement a separate CustomUserDetailsService instead of defining 
    the bean inside SecurityConfig?
--------------------------------------------------------------------------------
ANSWER:
"Defining the UserDetailsService bean directly inside SecurityConfig causes a 
circular dependency error (BeanCurrentlyInCreationException).

This is because SecurityConfig needs to inject JwtAuthenticationFilter, which in 
turn needs to inject UserDetailsService. If UserDetailsService is defined inside 
SecurityConfig, Spring enters an infinite loop trying to construct SecurityConfig.

By creating a separate CustomUserDetailsService class annotated with @Service, 
we break this loop, keep our code clean, and separate database-specific user-loading 
logic from security filter chain configuration."

Q10: Walk me through the detailed execution flow of JWT Login (Credentials Authentication)
--------------------------------------------------------------------------------
ANSWER:
"1. HTTP POST request containing credentials (username, password) is sent to /api/v1/auth/login.
2. The request passes the filter chain because this path is configured as .permitAll().
3. DispatcherServlet routes the request to AuthController.loginUser(), which delegates to UserService.loginUser().
4. Inside the service, we instantiate a UsernamePasswordAuthenticationToken and pass it to the AuthenticationManager.
5. The manager delegates to DaoAuthenticationProvider, which loads user credentials via our CustomUserDetailsService from the PostgreSQL database.
6. The provider calls PasswordEncoder.matches() to compare the incoming password with the hashed database password.
7. If authenticated, the manager returns the principal. The service extracts the canonical username, calls JwtUtils.generateToken(), and returns a LoginResponse containing the JWT token."

--------------------------------------------------------------------------------
Q11: Walk me through the execution flow of JWT Request Validation for secure endpoints
--------------------------------------------------------------------------------
ANSWER:
"1. Client calls a secure endpoint (e.g. GET /api/v1/users) sending the header: 'Authorization: Bearer <token>'.
2. The request enters the filter chain and is intercepted by JwtAuthenticationFilter (OncePerRequestFilter).
3. The filter extracts the raw token from the header by stripping the 'Bearer ' prefix.
4. The filter calls JwtUtils.validateToken() to verify the signature and expiration against the secret key.
5. If valid, the filter extracts the username (subject) and loads the UserDetails from the database via CustomUserDetailsService to verify the user still exists and fetch roles.
6. The filter creates a UsernamePasswordAuthenticationToken and injects it into Spring's static SecurityContextHolder.
7. The request proceeds down the chain. Spring Security checks the SecurityContext, authorizes the request, and allows DispatcherServlet to route it to UserController.getUsersList()."

Q12: How will OAuth2 Login integrate with our existing JWT-based Stateless Architecture?
--------------------------------------------------------------------------------
ANSWER:
"1. The user logs in via Google/GitHub OAuth2. The frontend obtains an authorization code and submits it to our backend at POST /api/v1/auth/oauth2/google.
2. The backend exchanges this code for Google's access token and requests the user profile details (email, providerId, names).
3. The backend checks if a User exists in our database with that email and provider. If not, it registers the user (setting provider = GOOGLE and leaving the password blank/random).
4. The backend then issues its own custom JWT token signed by our secret key.
5. The frontend receives our JWT token and uses it to authorize all subsequent requests to our secure endpoints. 
We issue our own token rather than reusing Google's token to keep our authorization roles, permissions, and token lifetimes independent of Google's APIs."

Q13: What is the difference between Lazy and Eager fetching in JPA/Hibernate? 
     What is the default fetch type for @OneToOne?
--------------------------------------------------------------------------------
ANSWER:
"Eager Fetching (FetchType.EAGER) means Hibernate automatically loads the associated 
child entity immediately at the same time it loads the parent entity (using database 
joins or secondary select queries).

Lazy Fetching (FetchType.LAZY) means Hibernate does not fetch the child database 
record until the getter method for the association is explicitly called in code. 
Instead, it puts a lightweight Proxy object in its place.

By default, in JPA, the @OneToOne and @ManyToOne associations default to EAGER 
fetching, while @OneToMany and @ManyToMany default to LAZY fetching. In production, 
we should always explicitly override @OneToOne to use LAZY fetching to avoid 
unnecessary joins and performance degradation."

--------------------------------------------------------------------------------
Q14: What do Cascade operations mean in Hibernate, and why do we use them?
--------------------------------------------------------------------------------
ANSWER:
"Cascade operations dictate how changes applied to a parent entity propagate to 
its child entities. For example, cascade = CascadeType.ALL propagation rules mean 
that if you persist, merge, refresh, or remove a parent object (like User), Hibernate 
will automatically execute the same action on the child object (like UserPreferences).

In the case of User and UserPreferences, we configure CascadeType.ALL because a 
preferences record cannot exist without a user. If we delete a User, their associated 
preferences should be automatically deleted (cascading the delete) to prevent orphan 
records and maintain database integrity."

Q15: How does the @OneToOne relationship Owning vs Inverse side mapping work? 
     What is the Hibernate Lazy Loading limitation on the inverse side?
--------------------------------------------------------------------------------
ANSWER:
"In a bidirectional @OneToOne relationship:
1. The Owning Side holds the foreign key column in the database and is mapped 
   using @JoinColumn. For example, UserPreferences is the owning side because its 
   table has the 'user_id' foreign key column pointing to the users_tbl table.
2. The Inverse Side is the referencing side and uses the 'mappedBy' attribute to 
   point to the field name in the owning class. For example, User has mappedBy = 'user'.

The Hibernate Lazy Loading Limitation:
In Hibernate, lazy loading on the inverse (referencing) side of a @OneToOne 
relationship is disabled by default—it is always eagerly loaded even if you write 
fetch = FetchType.LAZY. 

This is because the parent table (users_tbl) does not have a foreign key column to 
tell Hibernate whether the associated child record is null or exists. Hibernate is 
forced to execute a SELECT query on the child table immediately to determine if it 
should set the field to null or instantiate a proxy object. The owning side 
(UserPreferences), however, has the foreign key in its own table, so it can easily 
be lazy-loaded."

Q16: Why should you validate JWT in a Servlet Filter rather than a Spring MVC 
     Interceptor (HandlerInterceptor)?
--------------------------------------------------------------------------------
ANSWER:
"We validate JWTs in a Servlet Filter because of two core architectural reasons:

1. Scope of Control (Early Rejection): Servlet Filters execute early in the request 
   lifecycle at the web container level (Tomcat), before the request reaches Spring 
   MVC's DispatcherServlet. If a request carries an invalid, expired, or missing 
   token, we can reject it immediately (returning 401/403) without wasting server CPU 
   and memory on Spring MVC routing, controller mapping, and parameter resolution.
2. Spring Security Architecture: Spring Security is built entirely on a chain of 
   Servlet Filters. Endpoint authorization checks (e.g. .anyRequest().authenticated()) 
   occur within the filter chain. To authorize requests, the SecurityContextHolder 
   must be populated *before* authorization filters run. Interceptors run inside 
   Spring MVC, which is too late to set up this context."

Q17: Why is the doFilterInternal() method in our JwtAuthenticationFilter executed 
     first before the Controller mapping?
--------------------------------------------------------------------------------
ANSWER:
"The doFilterInternal() method is executed first because our filter extends Spring's 
OncePerRequestFilter, which is a Servlet Filter. 

In Java web applications, HTTP requests pass through the Servlet Container (Tomcat) 
first. Tomcat executes a chain of registered filters (the FilterChain) before delegating 
the request to Spring MVC's DispatcherServlet. 

Since Spring Security is a chain of servlet filters, and we inserted our custom 
JwtAuthenticationFilter into this chain using '.addFilterBefore(...)', Tomcat intercepts 
the incoming request early, runs our doFilterInternal() logic to validate the JWT, 
and only forwards the request to DispatcherServlet (and eventually to the Controller) 
after our filter explicitly calls 'filterChain.doFilter(request, response)'."

Q18: Why do we use @Transactional(readOnly = true) for read operations, and what 
     optimizations does it provide under the hood in Spring/Hibernate?
--------------------------------------------------------------------------------
ANSWER:
"We use @Transactional(readOnly = true) for read-only operations (like fetching profiles 
or preferences) to achieve three major performance optimizations:

1. Disabling Dirty Checking (Hibernate level): By default, Hibernate keeps an in-memory 
   copy (snapshot) of every loaded entity. At the end of a transaction, it compares 
   the entity's current state with the snapshot to see if it needs to execute an UPDATE 
   statement (Dirty Checking). With readOnly = true, Hibernate disables dirty checking, 
   saving CPU and memory by not storing snapshots or performing comparison checks.
2. Manual Flush Mode (Hibernate level): Hibernate sets the FlushMode to MANUAL. This 
   prevents automatic flushes of SQL statements during database reads, saving database 
   write locks and roundtrips.
3. Connection Level Optimization (JDBC/DB level): Spring passes this flag to the 
   JDBC driver, calling 'connection.setReadOnly(true)'. If the database supports it 
   (like PostgreSQL), this allows the database to optimize locking strategies, query 
   execution plans, and safely route queries to read-only replica databases."

Q19: In our User-UserPreferences bidirectional relationship, how does saving the 
     parent User automatically update the child preferences without calling save 
     on a separate preferences repository?
--------------------------------------------------------------------------------
ANSWER:
"This is achieved using JPA Cascading. In the User entity, we configured the association 
with: 

    @OneToOne(mappedBy = "user", cascade = CascadeType.ALL, fetch = FetchType.LAZY)

The cascade = CascadeType.ALL setting dictates that any persistence operations (such 
as persist, merge, or save) performed on the parent User entity propagate automatically 
to the associated UserPreferences entity.

Furthermore, inside a @Transactional boundary:
1. The User entity and its linked UserPreferences are loaded into the Hibernate 
   Persistence Context, making them 'Managed' entities.
2. When we modify fields on the preferences object, Hibernate's dirty checking mechanism 
   detects these changes at transaction commit time.
3. Hibernate automatically executes the appropriate SQL UPDATE on user_preferences_tbl 
   to synchronize the state, even without calling save() explicitly."

Q20: Why should you create a custom wrapper (like PaginatedUserResponse) instead of 
     returning Spring Data's Page<User> directly from the REST Controller?
--------------------------------------------------------------------------------
ANSWER:
"We avoid returning Spring Data's Page<T> directly from Controllers for three key 
architectural reasons:

1. Decoupling the API Contract: Page<T> is a framework-specific class belonging to 
   Spring Data. If we return it directly, our external REST API contract is tightly 
   coupled to our persistence framework. If we ever migrate away from Spring Data JPA 
   (e.g., to MyBatis or bare JDBC), our API response format would break. Using a custom 
   DTO record ensures our API contract remains stable regardless of internal framework 
   changes.
2. Serialization Control (Response Cleanliness): The Page<T> object contains a lot 
   of framework-internal metadata (like complex Pageable and Sort nested objects) 
   that is serialized into JSON by default. This makes the JSON response bloated and 
   hard for frontend developers to parse. A custom DTO allows us to serialize only the 
   necessary metadata (like pageNo, pageSize, totalElements, totalPages, last).
3. Entity Encapsulation: We must never leak database entities (User) inside the Page 
   content list. Mapping the Page content to a list of UserResponseDTO inside a custom 
   wrapper enforces strict security boundaries, preventing the leakage of passwords or 
   sensitive fields."

Q21: Why is Google OAuth2 not a replacement for our local JWT architecture? How 
     do they work together to solve different problems?
--------------------------------------------------------------------------------
ANSWER:
"Google OAuth2 and local JWTs are not competing technologies; they serve completely 
different purposes in a secure web application:

1. Authentication vs. Session Authorization: Google OAuth2 acts as the Authentication 
   mechanism (Federated SSO). It verifies the user's identity (answering 'Who is this 
   user?'). Our local JWT is the Authorization & Session mechanism (answering 'Does 
   this user have access to our APIs, and what are their roles?').
2. Decoupling & API Performance: If we used Google's access token directly for our 
   endpoints, our backend would need to call Google's API on every single incoming request 
   to validate the token. This creates a single point of failure (if Google is down, 
   our app is down) and heavily degrades performance due to network latency. By exchanging 
   Google's code for our own JWT once during login, subsequent requests are validated 
   statelessly in milliseconds.
3. Identity Merging: Our local database is the single source of truth. A user can log 
   in via email/password, Google, or GitHub. By mapping the external provider profile 
   to our local User record and issuing a unified local JWT, our resource endpoints 
   remain clean, consistent, and independent of the login method."

Q22: Why is database-level cascade (ON DELETE CASCADE via @OnDelete) preferred 
     over JPA-level cascade (CascadeType.ALL) for parent-child deletions in production?
--------------------------------------------------------------------------------
ANSWER:
"We prefer database-level cascades (@OnDelete) over JPA-level cascades (CascadeType.ALL) 
for large-scale deletions due to critical differences in query execution and performance:

1. JPA-Level Cascade (CascadeType.ALL): Hibernate must load all child entities (e.g., 
   10,000 tasks) into the JVM memory (Persistence Context) to track their state changes, 
   and then execute 10,000 individual SQL DELETE queries. This causes excessive memory 
   consumption, high CPU load, network latency, and severe database locking.
2. Database-Level Cascade (@OnDelete): Hibernate only issues a single query to delete 
   the parent row (e.g., DELETE FROM users_tbl WHERE id = ?). The database engine itself 
   automatically handles the deletion of all corresponding child rows in tasks_tbl/projects_tbl 
   in a single, native database operation. This reduces network round-trips from 10,000 
   to 1, optimizing execution speed and transaction safety."

Q23: How do Spring's @Transactional proxy mechanics and Transaction Manager 
     handle coordinate updates across multiple operations (like task update and goal progress)?
--------------------------------------------------------------------------------
ANSWER:
"Spring coordinates multi-entity operations (e.g., saving a Task and updating the Goal) 
inside a single transactional boundary using AOP Proxies and the Transaction Manager:

1. AOP Proxy Interception: When a method (like updateTask) annotated with @Transactional 
   is invoked, Spring's proxy intercepts the call. It opens a physical database connection, 
   disables auto-commit (connection.setAutoCommit(false)), and binds this connection to 
   the current executing thread using TransactionSynchronizationManager.
2. Connection Reuse (Propagation): Under the hood, default propagation (Propagation.REQUIRED) 
   ensures that subsequent database operations (e.g., countByGoal, countByGoalAndStatus, 
   goalRepository.save) executed within the method share the exact same database connection 
   and transaction block.
3. Commit/Rollback Resolution: If the method returns normally, the proxy commits the 
   transaction (connection.commit()). If any RuntimeException or Error is thrown during 
   execution (e.g., validation fail, entity not found, database lock), the proxy intercepts 
   the exception and issues a rollback (connection.rollback()), ensuring all tables return 
   to their original consistent state."

Q24: Why should you configure JSON Serialization (like GenericJackson2JsonRedisSerializer) 
     for Redis values instead of using Spring's default JDK Binary Serializer?
--------------------------------------------------------------------------------
ANSWER:
"We configure JSON Serialization for Redis caching in production for three key 
architectural reasons:

1. Class Resiliency (Deserialization Safety): Spring's default JDK Serializer relies 
   on a serialVersionUID. If we cache a Java object, and then modify that class (e.g., 
   adding, renaming, or deleting fields) and redeploy, reading the old binary cache data 
   will cause a SerializationException and crash. JSON serialization is resilient to class 
   changes (Jackson simply ignores missing or extra fields during binding).
2. Interoperability (Cross-Platform): JDK binary serialization is specific to Java. If 
   other services in our architecture written in Node.js, Python, or Go need to access 
   or modify the Redis cache, they cannot decode Java binary streams. JSON is universal, 
   allowing seamless cross-platform sharing.
3. Readability & Debugging: Raw binary data stored in Redis is unreadable to developers 
   using Redis CLI or GUI tools. Serializing as JSON stores data as clean strings, making 
   it trivial to inspect, debug, and manually adjust values in the cache during testing."

Q25: Why is ThreadPoolTaskExecutor mandatory in production, and how do we prevent 
     concurrency race conditions (lost updates) in a distributed backend environment?
--------------------------------------------------------------------------------
ANSWER:
"We use ThreadPoolTaskExecutor to bound memory and thread creation. In production, we 
prevent concurrency issues differently based on the scope:

1. JVM-Level Concurrency (Single Node): For in-memory shared resources, we can use Java's 
   synchronized blocks, ReentrantLock, or Concurrent collections (like ConcurrentHashMap).
2. Distributed Backend Concurrency (Multiple Nodes): In a real-world web application 
   running behind a load balancer, Java's synchronized keyword does not work because it 
   cannot synchronize across different JVM instances. To prevent race conditions on database 
   records, we must use:
   - Optimistic Locking: Uses a @Version field on the JPA entity. If two threads read the 
     same row and try to update it, the first commit succeeds and increments the version. 
     The second commit fails with an OptimisticLockException.
   - Pessimistic Locking: Instructs the database to lock the row natively using SELECT ... 
     FOR UPDATE, forcing other transactions to block and wait.
   - Distributed Locks (Redis/Redlock): Acquires a shared lock key in Redis before running 
     the critical section."

Q26: Why should email-sending operations always be executed asynchronously in a 
     REST API environment? What happens if they are executed synchronously?
--------------------------------------------------------------------------------
ANSWER:
"We must always execute email sending asynchronously in production REST APIs for three 
critical reasons:

1. Request Thread Blocking (Latency): Connecting to an external SMTP mail server (like 
   Gmail or SendGrid), performing SMTP handshake, transmitting the payload, and waiting 
   for the SMTP response is a slow I/O bound network operation that typically takes **1 
   to 5 seconds**. If run synchronously on the HTTP request thread, the client's API call 
   is blocked, causing a terrible user experience (e.g., the signup button spins for 
   5 seconds). Offloading it to a background thread pool returns the HTTP response in 
   milliseconds.
2. Single Point of Failure: If the external mail server is slow or temporarily down, 
   a synchronous email call would throw an exception that could fail the entire client 
   request. If a user registers successfully but SMTP fails, the transaction would rollback 
   and the user account creation would fail. Async execution decouples the main business transaction 
   from the notification delivery.
3. Thread Exhaustion: Under high traffic, synchronous I/O blocks the Tomcat request thread 
   pool. When all available threads are blocked waiting for slow SMTP handshakes, the application 
   server cannot accept new HTTP requests, leading to server timeouts and system failure."

Q28: How do you guarantee in Docker Compose that a Spring Boot application only 
     starts after the PostgreSQL database and Redis cache are fully ready to accept connections?
--------------------------------------------------------------------------------
ANSWER:
"In Docker Compose, simply declaring `depends_on: [db, redis]` is NOT sufficient because 
Docker only waits for the database/cache container processes to *start*, not for them to 
be ready to accept connections. If the Spring Boot app starts before the database finishes 
initialization, it will crash immediately.

To guarantee correct startup ordering, we must combine `depends_on` with **Healthchecks**:

1. Define Healthchecks: In the db/redis services, we define a health probe.
   - For PostgreSQL: `pg_isready -U postgres -d dbname`
   - For Redis: `redis-cli ping`
2. Conditional Dependency: In the Spring Boot app service, we configure `depends_on` 
   with conditions:
   ```yaml
   depends_on:
     db:
       condition: service_healthy
     redis:
       condition: service_healthy
   ```
This forces the Docker Engine to block the Spring Boot container startup until the database 
and Redis health probes return successfully (healthy), preventing connection failures."

Q29: How do you write a custom HealthIndicator in Spring Boot, and how does Actuator 
     determine the final aggregated application health status?
--------------------------------------------------------------------------------
ANSWER:
"We write a custom health indicator in Spring Boot to expose custom status checks (like 
SMTP connections or database counts) by implementing the `HealthIndicator` interface:

1. Custom Health Indicator: We declare a Spring component and override the `health()` method:
   ```java
   @Component
   public class MyHealthIndicator implements HealthIndicator {
       public Health health() {
           boolean isUp = checkConnection();
           return isUp ? Health.up().build() : Health.down().withDetail("err", "Reason").build();
       }
   }
   ```
2. Auto-Discovery: Spring Boot Actuator automatically scans all beans implementing the 
   `HealthIndicator` interface and aggregates them into the `/actuator/health` response.
3. Aggregation Strategy: Under the hood, Spring uses a `HealthContributorRegistry` and 
   a `StatusAggregator` (typically `OrderedStatusAggregator`). It aggregates all child 
   probes (db, diskSpace, ping, and custom indicators) into a single top-level status. If 
   ANY single health probe reports `DOWN` or `OUT_OF_SERVICE`, the aggregator marks the overall 
   status as `DOWN` (priority: DOWN > OUT_OF_SERVICE > UP > UNKNOWN), failing Kubernetes readiness probes."

Q30: What is a Consumer Group in Apache Kafka? How does it partition ownership, 
     and what happens if the number of consumers exceeds the number of partitions?
--------------------------------------------------------------------------------
ANSWER:
"A Consumer Group is a collection of consumers that cooperate to consume messages from 
a set of topics. It is Kafka's primary mechanism for scaling consumption throughput:

1. Partition Distribution: Kafka guarantees that each partition in a topic is consumed 
   by exactly one consumer member within a specific group. If a topic has 4 partitions 
   and our group has 2 consumers, each consumer is assigned 2 partitions.
2. Horizontal Scaling: If the consumption load increases, we can add more consumers 
   to the group. Kafka automatically triggers a **Rebalance** to redistribute partitions. 
   If we have 4 partitions and 4 consumers, each consumer gets 1 partition.
3. Exceeding Partition Limits: If we add a 5th consumer to a group listening to a topic 
   with 4 partitions, the 5th consumer will remain **idle** (assigned 0 partitions). Kafka 
   never allows two consumers in the same group to read from the same partition simultaneously 
   (to guarantee message processing order within a partition). To scale beyond this limit, 
   we must increase the topic's partition count."

Q31: What is the difference between `@Mock`, `@Spy`, and `@MockBean` in Spring Boot tests, 
     and when should you use each?
--------------------------------------------------------------------------------
ANSWER:
"These three annotations serve different purposes in unit and integration testing:

1. `@Mock` (Mockito):
   - Scope: Pure JUnit unit testing (no Spring context loaded).
   - Behavior: Creates a complete mock instance of a class. Every method call returns default 
     values (null, 0, false) unless stubbed (using `when().thenReturn()`).
   - Usage: Used alongside `@ExtendWith(MockitoExtension.class)` to test services in isolation.

2. `@Spy` (Mockito):
   - Scope: Pure JUnit unit testing (no Spring context loaded).
   - Behavior: Creates a partial mock wrapper around a real instance of a class. It calls the 
     actual code of the class by default, but allows you to stub specific methods.
   - Usage: Used when you want to track or mock specific methods on a class while executing 
     real logic for the rest.

3. `@MockBean` (Spring Boot Test):
   - Scope: Spring Integration testing (loads the Spring `ApplicationContext`).
   - Behavior: Creates a Mockito mock and registers it inside the active Spring Boot test 
     `ApplicationContext`. It automatically replaces any existing bean of the same type.
   - Usage: Used in `@SpringBootTest` or `@WebMvcTest` to stub external interfaces (like mail 
     senders or payment gateways) while letting Spring wire the rest of the application context."

Q32: What is an HTTP Interceptor in a frontend Single Page Application (SPA), 
     and how does it implement seamless JWT access token refresh under the hood?
--------------------------------------------------------------------------------
ANSWER:
"An HTTP Interceptor is a configuration layer in a client-side API engine (like Axios 
interceptors or custom fetch wrappers) that intercepts outgoing requests before they leave 
the client, and incoming responses before they are processed by calling components.

1. Outgoing Hook: The interceptor automatically injects the stored `Authorization: Bearer <token>` 
   header to outgoing HTTP requests, eliminating manual boilerplate across components.
2. Incoming Hook (401 Trapping): If the backend responds with a `401 Unauthorized` status (indicating 
   the access token has expired), the interceptor halts the user execution flow.
3. Silent Rotation: In the background, the interceptor sends a request to the `/api/v1/auth/refresh` 
   endpoint with the `refreshToken`.
   - If successful, it stores the new access/refresh tokens in localStorage.
   - It then updates the headers on the original failed request with the new access token and 
     resends it, creating a seamless user experience.
   - If the refresh token is also expired or invalid, it clears credentials and redirects the user 
     to the login screen."
